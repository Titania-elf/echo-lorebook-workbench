# 全文调度流程落地方案

本方案落实已经讨论确定的流程，直接作为实现与后续检查的依据。

## 本轮生成流程

1. 沿用酒馆的生成前拦截入口，等待调度完成后继续原来的正文请求。
2. 使用本次生成采用的聊天文本，读取配置的最近 N 层有效发言，不截断每层文本；正常发送包含新消息，重生成和续写沿用酒馆准备的历史。
3. 仅处理当前聊天挂载、且已勾选托管的世界书。读取已保存内容并核对原生读取快照，读取失败时明确跳过本轮调度。
4. 已启用且符合角色、生成类型等明确限制的蓝灯默认全部保留。蓝灯不交给模型选择，也不占绿灯数量／Token 上限。
5. 绿灯的手动固定、排除继续生效。向调度模型提供完整蓝灯正文、固定绿灯正文及可选绿灯正文，附标题、关键词和标识，不用摘要代替正文。
6. 模型返回本轮需要的绿灯标识与理由，允许空选择；程序检查标识、去重和绿灯预算，再取原条目内容。
7. 前置条目进入“世界书之前”，后置条目进入“世界书之后”。原来使用深度、作者注释、出口等位置的托管条目，本轮映射到后置，不修改原书属性。
8. 失败时取消本轮调度结果，恢复原生世界书路径，立即放行正文；在酒馆页面顶部显示原因和已跳过说明。

纯向量条目继续走酒馆原生路径。AI 目录概括保留为辅助展示功能，全文筛选不依赖目录摘要。旧场景记忆只作参考，不自动沿用上轮绿灯。

## 酒馆接入方式

- 在 `WORLDINFO_ENTRIES_LOADED` 中只修改本次读取的条目副本，暂时关闭由本轮调度接管的蓝／绿条目，避免原生扫描重复加入或耗用预算。
- 在 `WORLDINFO_SCAN_DONE` 的激活集合中加入本轮确认的条目副本，统一映射到前／后位置，由酒馆继续完成世界书正则处理、排序、格式化和提示词构造。
- 注入使用本轮标识和同一个扫描集合，重复扫描只加入一次；不反写世界书文件或共享原生缓存。
- 临时副本保留恢复信息。取消、聊天变化、设置变化或合并异常时撤销本轮注入与临时覆盖，防止旧结果用于另一轮。已经跳过托管条目的原生扫描按原聊天重新完成一次；在这次恢复的最后一轮先取激活内容，将正则、格式化和计时处理留给原来的扫描，避免递归次数上限阻止恢复。
- 上述撤销用于资料交给原生构造之前。原生世界书已完成构造后结束辅助筛选，收起取消辅助请求按钮；后续修改从下一轮生效，正文停止仍走酒馆的原停止操作。
- 普通回复、重生成、滑动重写和续写运行该流程；辅助模型请求、静默生成及原生提示预览保持原有入口。

## 结果与提示

- 分别展示读取楼层数、蓝灯常驻数量、绿灯候选数量、本轮绿灯选择及前／后位置。
- 显示本轮是否调用了筛选 API。没有可选绿灯时直接使用蓝灯和固定绿灯。
- 世界书构造接纳情况与选择结果分开展示，不把试选当作正文已经发出。
- 顶部失败通知在工作台关闭时也可见，不需要确认，不阻塞正文。

## 修改范围

- `core.js`：完整历史／正文输入、蓝绿划分、绿灯选择与预算、原书版本指纹。
- `director.js`：本轮生命周期、原生扫描接入、失败放行及结果记录。
- `native-adapter.js`：当前挂载书的已保存快照、原生明确限制、前后标记可用性及原生恢复。
- `scheduler-native.js`：本轮副本的归属、激活集合注入及撤销，保留尚未完成扫描的恢复信息。
- `scheduler-report.js`：蓝绿数量、API 提交状态与构造接纳文案。
- `index.js`、通知与调度视图：事件衔接、顶部通知、蓝绿结果与文案。
- `README.md`：实际使用流程和生效边界。
